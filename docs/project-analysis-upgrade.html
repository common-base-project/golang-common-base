golang-common-base 项目分析与升级方案

基于当前仓库代码、配置与依赖情况的评估结论：建议进行分阶段优化与升级，重点解决安全风险、技术债与可维护性问题。

1. 项目简介

  • 技术栈：Go + Gin + GORM + MySQL + Viper + Zap + Swagger。
  • 定位：后端基础脚手架，包含用户管理、邮件处理、JWT 鉴权、Swagger 文档、Docker/K8s 部署支持。
  • 入口：app/cmd/main.go，路由装配：app/router，业务模块位于 app/handler / app/models。

  • 项目结构清晰，分层相对明确（router/handler/model/pkg）。

3. 关键问题与风险

  • Go 版本较旧（1.18），影响性能、安全补丁与新特性使用。
  • github.com/dgrijalva/jwt-go 已停更，应迁移至 github.com/golang-jwt/jwt/v5。
  • github.com/streadway/amqp 标记 deprecated，应迁移至 github.com/rabbitmq/amqp091-go。
  • 配置样例中包含明文敏感信息示例（JWT secret、邮箱密码），需治理。
  • 鉴权中间件使用全局可变 Token 实例，存在并发安全隐患。
技术债 安全风险 并发风险

4. 是否需要优化和升级？结论

需要，且建议尽快执行。 当前项目具备继续演进的良好基础，但在依赖版本、安全治理和工程规范方面存在明显优化空间。建议采用“先安全、再稳定、后体验”的节奏推进升级，避免一次性大改带来不可控风险。

6. 升级流程（建议执行路径）

步骤 1：准备阶段
冻结主分支，建立升级分支，补充最小回归用例与接口清单。
步骤 2：基础升级
先升级 Go 版本与构建环境（本地、CI、Dockerfile）。
步骤 3：安全替换
优先替换 JWT 与 AMQP 的弃用库，修正调用差异。
步骤 4：框架升级
升级 Gin/GORM/Viper/Swagger 相关包并逐项回归。
步骤 5：配置治理
将明文密钥改为环境变量/密钥管理，清理默认弱配置。
步骤 6：发布验证
灰度发布 + 监控告警 + 回滚预案演练。

7. 升级需求清单（交付视角）

功能与质量需求

  • 所有现有 API 保持兼容（或明确版本化变更）。
  • 认证、邮件、分页、数据库 CRUD 完整回归。
  • 构建、启动、容器部署流程保持可用。

安全与运维需求

  • 敏感配置全部外置，不在配置文件中明文存储。
  • 依赖升级后进行漏洞扫描与基线检查。
  • 上线必须具备监控、日志、告警与回滚脚本。

8. 分阶段目标（推荐）

  • Phase A（高优先）：Go 版本升级 + JWT/AMQP 替换 + 敏感配置治理。
  • Phase B（中优先）：Gin/GORM/Viper/Resty/Zap 等核心依赖升级与回归。
  • Phase C（持续优化）：并发安全改进（如移除中间件全局状态）、CI 自动化测试增强、文档补齐。
